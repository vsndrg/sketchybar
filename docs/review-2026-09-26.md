## Bugs

### B1. [HIGH] F6: iPad returns only after ~30 s (reproduced, root cause)
`barhelper sleep` calls `exit(0)` inside the `NSWorkspace.willSleepNotification` handler
(`helper/main.swift:1519-1521`). The kernel waits for the process's ack in tellChangeDown, the
process dies without it → sleep stalls exactly 30 s (timeout 0x7530). Screen is off but
Bluetooth/AWDL are already down → Sidecar device unavailable; the Mac never actually sleeps
(no `Sleep` in `pmset -g log`), `didWake` arrives only at the timeout. Regression from b7414d4:
software sleeps before it took ~1 s, all after it exactly 30 s; lid sleeps ~1 s throughout.
A/B with the user (13:09–13:12):
- E1 real `barhelper sleep`: 30 s stall, iPad back after 36 s (`E/sleep.log.E1`).
- E2 same without exit in the handler (`E/sleepvariant.swift noexit`): sleeps in 1 s, real sleep,
  iPad back 6 s after wake.
- E3 variant with exit in the handler: 30 s again.
Logs: `E/observer.log`, `E/sleepvariant.log`, `E/sleep.log.E1-E3`.
"Never comes back" = the same window: F6 at 12:50:38, at 12:51:01 System Settings showed only the
Mac, at 12:51:13 the daemon connected the iPad.
Fix: don't exit in willSleep — F6 process doesn't subscribe to willSleep and exits itself 1–2 s
after `IOPMSleepSystem` (or exits on a timer / after wake); move "sleep didn't happen" to the daemon.

### B2. [MEDIUM] Two parallel reconnect loops
`screenIsUnlocked` → `start()` (line 1436), then `didWake` → `start()` again (1459-1471) without a
`running` check, `attempts` reset. Two loops call connectToDevice → "The device is already in use."
Seen in E1, E3 and at 12:51 (two "not available yet" in the same second). Fix: `guard !running`.

### B3. [LOW] F6 truncates sleep.log
`main.swift:1514` `createFile` on every F6 — erased the 12:49 lid-close record. Append + cap size.

### B4. Lid close: "iPad doesn't reconnect" NOT reproduced; races found
Lid on battery (E4): back 8 s after opening (first try "The device was disconnected", second ok).
On charger (E5): 3 s. Morning lid closes (12:49:36, 12:50:04, 12:50:20) also reconnected in 4–15 s.
At 12:48 the iPad didn't return because it was disconnected at 04:44:23, 6 min before sleep at
04:50 — outside the "lost ≤30 s before sleep" rule, correct. Likely the user's "never returns"
was B1 (F6 right after the lid experiments).
Suspected from code:
- (a) On charger the iPad drops BEFORE willSleep: screen change at 13:22:34.111 (main becomes the
  iPad, then the virtual 1920×1080), willSleep at 34.447. `sketchybarrc:69-72` geometry check waits
  1.0 s; if `system_will_sleep` (line 84) comes >~1 s late, the bar reloads and pkill kills the
  daemon; the "lost" map is memory-only, the reconnect file is written only in willSleep → the new
  daemon knows nothing. Margin in E5 was 0.66 s.
- (b) >30 s between loss and willSleep → iPad falls out of "recent" (line 1451).
Fix: write `want` to the file on loss (in `track()`), and/or don't reload while main is the iPad
or the virtual display.
"iPad shows its wallpaper, then fades" is macOS behaviour (session ends at sleep, iPad auto-locks).
Possible improvement: disconnect explicitly in the daemon's willSleep, delaying sleep via
`IORegisterForSystemPower` + `IOAllowPowerChange`.

### Findings (by gain/effort)
**P1. Read-only bar queries run a full AeroSpace session (big gain, small patch).** Every CLI command
incl. `list-*` goes through `runLightSession(.socketServer…)`
(`~/.cache/aerospace-src/Sources/AppBundle/server.swift:95`) → `layoutWorkspaces()` (with the flicker
patch waits) + `scheduleRefreshSession` (`layout/refresh.swift:88-89`, AX poll of all apps). The bar
does 4 per switch (`items/spaces.lua:209-275`, two refreshes × 2 CLI), 6 cross-monitor.
A/B (`spaces.events updates=off/on`), same monitor, per switch: light sessions 6 vs 2, refresh 10 vs
7, AX get 206 vs 88, AX set 66 vs 26; AeroSpace CPU for 12 switches 1.28–1.57 s vs 0.68–0.74 s.
Cross-monitor: 10 light sessions, 314 AX get, 136 AX set though no window moves (repeated setFrame,
IPC into Telegram/WezTerm); quiet only at ~800 ms. cmd-k inside accordion: nothing changes, 6
sessions, ~190 get / ~80 set. First `list-workspaces` during a switch 60–220 ms (waits for main
actor, itself lays out with drain up to 150 ms).
Fix: run `list-*` directly on the main actor without `runLightSession`. Expect AeroSpace CPU/switch
×0.5, AX traffic ÷2–3, bar reconcile 100–150 ms earlier, cmd-shift-N cached 185–230 → ~120–150 ms.
Risk: query sees the model as of the last session; bar refreshes are event-driven after sessions.

**P2. `barhelper render` spawn: 40 ms startup + 40–65 ms icon loading per process.**
Global `let backing = NSScreen.screens…` (`helper/main.swift:63`) runs for every subcommand (~33 of
40 ms). `iconCache` is per process (`main.swift:334-342`): 8 icons via NSWorkspace 10–17 ms, first
draw 28–49 ms. Variant without NSScreen (`E/variant`): `render '[]'` 40 → 8 ms, 2 status rows
57 → 26.5, spaces 63 → 63 (AppKit icons).
(a) pass scale in the job JSON (Lua has `config.screen.scale`), lazy `backing`: −31 ms per status
render, `screens`, `cursor`. (b) disk cache of icons/SF Symbols as PNG (bundle+size+icon_theme),
ImageIO without AppKit → spaces render ~15–20 ms. (c) render in the daemon (icons in memory),
Lua `sbar.exec("… | nc -U sock")`, still async; warm row ~4 ms.
cmd-shift-N miss 334 → ~220 (a+b) → ~130–150 ms (c); 24-image prerender 200/125 → ~90 ms; first
theme apply ~1.1 s → ÷3–5. Constraints kept (same content-addressed PNGs, image swap only).

**P3. Bar clicks: extra `barhelper cursor` spawn + race.** `items/spaces.lua:305` and `items/status.lua`
(clicked) spawn `barhelper cursor` (42 ms idle, 85–110 at click time) before `aerospace workspace N`.
Cursor read 40–150 ms after the click → moving the mouse away loses the click (3/6 synthetic clicks
with mouse leaving after 80 ms did nothing). Fix: take the target from `d.hovered` (same regions as
bar_hover), `cursor` only as fallback when `hovered == 0`; add `input`/`clock` regions to status.
Or the daemon (already sees clicks globally) fires `bar_click REGION=…`. 220–255 → ~130–150 ms.

**P4. Daemon mouse tracking CPU.** Global NSEvent monitor (`main.swift:1236`) ~0.37 ms/event → 4.3 %
of a core on any mouse move (~8× with a 1000 Hz mouse). Over the bar `checkHover` calls
`FileManager.attributesOfItem` per move — `loadRegions` (`main.swift:1130`) and `Tooltips.load`
(`main.swift:841`), ~90 % of checkHover → 12.5 %. Fix: listen-only `CGEventTap` for mouseMoved
(measured 134 vs 475 ms CPU / 1200 events → ~1.2 %; no permission needed for mouse; re-enable on
`tapDisabledByTimeout`); regions/tooltips via DispatchSource watcher like `Menu.watch` (or `stat(2)`),
another ~−3 %; cache screen frames (update on `didChangeScreenParameters`) instead of
`NSScreen.screens` per event.

**P5. Bar refresh: two sequential CLI calls via `sh`, twice per switch.** One pair 55 ms idle,
90–230 ms during a switch (`spaces.lua:209-222`, chained via `again` at `:254`). Run in parallel or
replace with one `list-windows` (workspace, monitor, visible, focused) + `list-workspaces --visible`;
one final refresh per burst (the predicted image already gives the instant update). 4 CLI → 2.

**P6. Redundant renders.** No in-flight tracking (`lib/render.lua:72-88`): the same 4-job batch sent
twice 163 ms apart (prerender from consecutive `show()`s) — track outputs being rendered. Hover
variants prerender (`spaces.lua:172`): every hover change spawns ~6 images (70–150 ms CPU); needed
only for keyboard switches with the cursor resting on the bar → render lazily (rare miss ~60 ms).
Volume: each `show()` hashes D + 2(E−1)·D jobs (26 at E=7, D=2: 2.8 ms Lua; E=10, D=3: 57, ~6 ms),
`show()` 3× per switch; a changed app set misses all 26 (2 spawns, ~330 ms wall). Status rendered
once per strip height (2 variants, justified).

**P7. Next-minute frame rendered every minute** (`status.lua:195`, 1 spawn ~29 ms CPU/min). Render
10–15 min ahead in one call (−50 spawns/h). Moot with P2c.

**P8. Daemon triggers via `Process()`** (`main.swift:39-45`): ~2.9 ms CPU in the parent vs 0.3 ms
`posix_spawn`, plus the sketchybar client ~4.6 ms CPU / 6–16 ms wall. Send the mach message
directly like SbarLua: −6–15 ms for hover/minute/menu.

**P9. Cache hygiene.** Startup deletes only files older than 60 min (`render.lua:14`), `gc` knows only
the current instance's files (`render.lua:105`) → 1660 files / 46 MB left. Add an async mtime pass
(don't touch pinned files).

For reference (no fix): sketchybar itself ~41 ms `--set` → screen (~40 % of a cached-hit latency),
Sidecar +15–25 ms. borders 20–24 ms CPU/switch, glow windows sized like the whole window (one
fullscreen border @2x ~29 MB). Karabiner-Elements spawns ~8 processes every ~3 s
(`core-daemons-enabled` loop) — outside these repos.

### Flicker patch waits vs. the "confirmed ordering" plan
Same monitor: new window appears at 97–165 ms, the old one hides 17–144 ms later (under the new
tile, invisible). Accordion: time to screen is the app's (Chrome applies a move 45–95 ms after the
request). On the iPad the flash mechanism is visible: the lower accordion window (Claude) lands
11–53 ms BEFORE the target (Chrome), because `drainAxQueues(target, ≤100 ms)` returns when the AX
call is done but Chromium moves asynchronously. Old Telegram stayed 50–94 ms after Chrome arrived,
so no flash was measured — but the margin is about the 150/80 ms bounds; a slow Chrome eats it.
Plan effect: time to target visible unchanged (app-bound); lower windows land ~20–50 ms later
(hidden under the target); final frame 0–60 ms earlier (confirmation one poll after the real landing
instead of "drain or 150 ms"); pure tiles lose the waits entirely → shorter sessions, fewer
interruptions. Probe: `CGWindowListCopyWindowInfo(onScreenOnly)` ~1.5–2 ms/call; poll off the main
actor every 4–8 ms only during a switch; ~1 s timeout for liveness only. P1 helps: bar queries
currently interleave into these waits and start new layout passes that stop the previous one from
hiding windows.

Caveats: AeroSpace dropped ~30–50 % of synthetic hotkeys (session tap got them all) — likely a
synthetic artifact, dropped runs excluded. The frame detector compares luma; theme changes keep
OKLCH lightness, so theme latency = spawns done + ~40 ms sketchybar.
